GeoPackage Creator v0.30.23
Release date: 2026-08-14

NEW in v0.30.23 (the actual root-cause fix for the crash open since v0.30.13 -
see chain below):

FULL CHAIN (so this fix's evidence stands on its own):
  v0.30.13  ABI guard added - refuses to compile the XSD on a libxml2 version
            mismatch. Correct diagnosis of a real defect, but blocked every
            conversion outright.
  v0.30.20  Pinned libxml2=2.14 in environment.yml, believing the VERSION
            mismatch was the whole crash. Tested on the real machine: pin
            worked (both tuples read (2,14,6)) and the SAME access violation
            still happened. WRONG THEORY - corrected in that changelog.
  v0.30.21  Diagnostic (8 subprocess probes, real machine): found the real
            differential - an etree.XMLSchema created BEFORE a GDAL write and
            still alive AFTER it crashes on next use or on being freed,
            independent of libxml2 version agreement.
  v0.30.22  Diagnostic (real machine): does GDAL disturb libxml2 state ONCE,
            or on EVERY write? Answer: EVERY write. A schema compiled safely
            after one write still crashes if a SECOND write happens before
            it's used again (P9). Only compiling fresh immediately before
            use and discarding immediately after survived 4 repeated cycles
            (P10).
  v0.30.23  (THIS RELEASE) Applies P10's proven-safe pattern to the shipped
            code.

- FIX (core/metadata_handler.py) - THE FIX. Removes the process-wide compiled-
  schema cache (_SHARED_SCHEMA, live since v0.30.10). MetadataHandler.schema
  is now a @property that compiles a brand-new etree.XMLSchema on EVERY
  access rather than reusing one cached object; validate_schema() compiles it
  inside the same lock as the parse/validate that follow, so its entire
  lifetime is contained in one call and can never span a GDAL write. Only the
  schema FILE's location is still cached (pure filesystem I/O, no libxml2
  state, independently confirmed safe). Public API unchanged - same class,
  same methods, same signatures. Performance cost: ~0.67ms per compile,
  measured directly; negligible against a conversion that takes seconds.
- NEW (dev_tools/run_release_check_v0.30.23.py) - adds a schema_no_cache
  regression guard (confirms .schema returns a DIFFERENT object on every
  access) and an 8-cycle real-batch-conversion stage that exercises the
  actual MetadataHandler class - real GDAL write, real
  generate_package_metadata(), real validate_schema(), repeated 8 times with
  one reused handler - in a crash-safe subprocess. This is the most direct
  real-machine test of this exact fix available short of a full conversion.

VERIFIED (Linux container, GDAL 3.8.4, lxml 6.1.1/2.14.6 matched - does NOT
  reproduce the crash regardless of this fix, see v0.30.20's entry for why):
  Full suite 304 passed, 1 skipped, 0 failed - no regression. handler.schema
  confirmed to return a DIFFERENT object on consecutive accesses (cache is
  genuinely gone). run_release_check_v0.30.23.py runs clean end-to-end
  including the new 8-cycle batch stage.

NOT YET VERIFIED - REQUIRED BEFORE SHIPPING:
  This fix has NOT been tested on the real Windows/Anaconda machine.
  v0.30.20's version-pin theory also looked solid after container testing and
  then failed on the real machine - a clean container run is necessary, not
  sufficient. Run on the target machine:
    conda activate geopackage
    python dev_tools\run_release_check_v0.30.23.py
  The stage that matters most is batch_conversion_cycle (stage 6) - 8 real
  write+validate cycles through the actual shipped MetadataHandler. If it and
  both pytest stages pass, the blocker open since v0.30.13 is very likely
  finally closed. Still required after that: a real GDB->GPKG conversion and
  DGIWG validation of the real output before distributing.

GeoPackage Creator v0.30.20
Release date: 2026-08-14

NEW in v0.30.20 (3 real bugs fixed; the libxml2 "root cause" claim was
DISPROVEN on the target machine - the blocker REMAINS OPEN):

*** READ FIRST - CORRECTION (2026-08-14) ***
  This release originally claimed the missing libxml2 pin was the root cause of
  the ABI blocker. A release check on the real Windows/Anaconda machine
  DISPROVED that. The pin works - LIBXML_COMPILED_VERSION and LIBXML_VERSION
  now BOTH read (2,14,6) - and the Windows access violation still occurs, at
  core/metadata_handler.py:526 (schema.validate), in test_converter.py,
  test_concurrency.py, and in a standalone probe with no project code.
  Version agreement was necessary but NOT sufficient.

  Genuine progress: MetadataHandler() now constructs for the first time since
  v0.30.13, because the ABI guard no longer fires. The crash therefore MOVED
  from "blocked at construction" to the real fault site.

  Leading hypothesis now: conda's lxml and conda's gdal each load their OWN
  libxml2 DLL. Two copies of the SAME version still keep separate global state
  (interned-string dicts, error-handler table), so a document from one copy
  validated against a schema owned by the other dereferences a pointer that is
  meaningless in the other's heap. Run dev_tools\diagnose_crash_v0.30.21.py -
  its Probe 0 counts the distinct libxml2 images in one process. If it reports
  2, the cause is settled.
*** END CORRECTION ***

- PARTIAL (environment.yml) - superseded, see CORRECTION above. Theory was:
  conda-forge's GLOBAL pinning file pins libxml2 to 2.14, and every conda-forge
  lxml binary is compiled against that - but conda-forge also publishes libxml2
  2.15.x, and the lxml recipe declares NO libxml2 constraint and NO
  run_exports. Nothing therefore stops the solver from installing libxml2
  2.15.3 (pulled in transitively by gdal) next to an lxml compiled against
  2.14.6 - exactly the observed LIBXML_COMPILED_VERSION (2,14,6) vs
  LIBXML_VERSION (2,15,3) fingerprint. This also explains why
  `conda env remove` + `conda env create` NEVER fixed it: a recreate re-runs
  the same unconstrained solve and re-picks 2.15.x. v0.30.19 speculated the
  env had simply never been genuinely recreated - that speculation was wrong.
  environment.yml now pins libxml2=2.14 explicitly. CONFIRMED to make the
  version tuples agree - and CONFIRMED INSUFFICIENT to stop the crash. The pin
  is retained because a version mismatch would be a real defect stacked on top
  of the actual one, but it is NOT the fix.
- FIX (core/gdal_handler.py) - create_geopackage() raises TimeoutError on lock
  contention, but its own trailing `except Exception` caught it and re-raised
  it as ValidationError (TimeoutError is an OSError subclass, so it was
  swallowed silently). Callers could not tell "another thread holds the write
  lock, retry" from "this output path is broken". A dedicated
  `except TimeoutError:` now re-raises it unchanged. NOTE: v0.30.19 listed the
  corresponding test as "possibly just flakiness from its tight 0.1s timeout" -
  it is NOT flaky, it failed 5/5 runs deterministically.
- FIX (tests/test_gdb_domains.py) - test_multiple_domain_types passed
  topic_category="utilities" and then asserted success. "utilities" is not in
  the ISO 19115 MD_TopicCategoryCode codelist; the correct value is
  "utilitiesCommunication", which core/config.py had right all along. The
  validator was correct and the TEST was wrong.
- HARDENING (defensive; does NOT manifest on the pinned GDAL 3.13.2) - dataset
  handles were tested for truth value at 7 sites. On GDAL >= 3.13 ogr.Open()
  and CreateDataSource() return a gdal.Dataset whose __bool__ is always True,
  so `if not ds:` is fine. On GDAL <= 3.12 they return an ogr.DataSource, which
  has __len__ (= GetLayerCount()) and NO __bool__ - so a valid, freshly created
  0-layer GeoPackage evaluates FALSY, making create_geopackage() raise "Failed
  to create GeoPackage" on success and close_geopackage() skip its whole close
  path (leaking the handle AND holding the write lock). All 7 sites now use
  `is None` / `is not None`. Separately, read_source_data() used
  driver.ShortName, which exists on gdal.Driver (3.13.2, so it worked) but not
  on ogr.Driver (<= 3.12, AttributeError reported as a misleading "Error
  reading source data") - now uses driver.GetName(), present on both. These are
  corrected because requirements.txt still admits GDAL >= 3.6.0 as a floor.

TESTED ON THE REAL MACHINE (2026-08-14, GDAL 3.13.2, lxml 6.1.1, Win 10):
  PASS environment / libxml2_abi MATCH (2,14,6) / gdal 3.13.2 /
       metadata_ctor (first success since v0.30.13) / version_strings
  FAIL gdal_lxml_interop  - NATIVE CRASH exit 3221225477 (0xC0000005)
  FAIL pytest_main        - Windows fatal exception: access violation
  FAIL pytest_concurrency - Windows fatal exception: access violation
  VERDICT: DO NOT SHIP.

  Crash site (reproducible):
    core/metadata_handler.py:526  validate_schema -> schema.validate(doc)
    core/metadata_handler.py:739  generate_package_metadata
    core/converter.py:588         convert
    tests/test_converter.py:143   test_convert_with_valid_shapefile

  A standalone probe (lxml XSD compile -> one GDAL vector write -> one further
  lxml call, NO project code) crashes identically, reproducing v0.30.12's
  finding. This is an environment/DLL-topology defect, not a logic defect in
  this codebase.

ALSO VERIFIED (Linux container, GDAL 3.8.4): full suite 304 passed, 0 failed,
  and the interop sequence does NOT crash there. That environment is NOT a
  valid proxy for Windows: on Linux lxml uses its own statically linked
  libxml2 while GDAL links the system one, so the two never share state. The
  three non-libxml2 fixes in this release are ordinary Python defects and are
  trustworthy; the libxml2 conclusion was not.

  Run dev_tools\diagnose_crash_v0.30.21.py. Probe 0 counts the distinct

NEW in v0.30.7 (concurrency crash fix + retracted GDAL diagnosis):
- RETRACTION: the "Windows fatal exception: access violation" first seen on
  2026-08-04 was initially attributed to GDAL 3.13.2. That was wrong. The
  environment had drifted from the pinned 3.13.1 to 3.13.2 at the same time
  the crash appeared, and correlation was read as cause. Evidence against it:
  core/validators.py was fixed at 12:22:03 on 2026-07-24, eight minutes AFTER
  the 12:14 run that is the only release test ever to complete; before that
  fix, concurrent threads aborted early on a fixed-filename write probe
  (".gpkg_creator_test") and never reached concurrent GDAL work on ANY GDAL
  version; the v0.30.6 per-thread source-copy mitigation changed nothing
  because the defect is on the OUTPUT side; and GDAL 3.13.2's release notes
  contain threading HARDENING, not a regression. GDAL_KNOWN_BAD_VERSIONS is
  now empty. The 3.13.1 pin is kept for reproducibility only.
- CRITICAL FIX (core/gdal_handler.py, core/converter.py): close_geopackage()
  ended with "del ds". ds is a parameter, so this unbound a local name and did
  NOT close the dataset - the caller's reference kept the GeoPackage open. In
  convert(), that reference (out_ds) then stayed in scope for the whole rest of
  the conversion, during which the same .gpkg is reopened through sqlite3 to
  embed metadata and finalize DGIWG compliance. Two live handles on one file,
  with the write lock ALREADY released so a second thread could start writing.
  Single-threaded this risks corruption; multi-threaded it is an access
  violation. close_geopackage() now flushes, calls FlushCache(), calls
  Dataset.Close() where available, and returns None so the caller drops its
  reference; convert() assigns that return over out_ds. The dataset is closed
  BEFORE the write lock is released.
- FIX (core/gdal_handler.py): close_all_datasets() had the same "del ds" no-op
  inside a for loop, where it also rebound each iteration. Datasets are now
  flushed and explicitly closed via _flush_and_close_dataset().
- FIX (core/gdal_handler.py): write-lock release. Four copies of
  "try: lock.release() except RuntimeError: pass" are replaced by
  _release_write_lock(), which tracks the acquired lock object and owning
  thread id. The swallowed exception hid two real bugs: releasing a lock the
  thread never owned, and - when acquire() timed out before
  _active_output_path was updated - releasing another conversion's lock.
- FIX (core/gdal_handler.py): gdal.UseExceptions()/ogr.UseExceptions() moved
  from GDALHandler.__init__ to module import. They mutate process-global
  binding state and swap the CPL error handler, so every thread constructing a
  handler raced on that global while other threads were inside GDAL.
- ADD (core/converter.py, core/config.py): conversions are now serialized
  process-wide via _serialize_conversions and a module-level lock, covering the

NEW in v0.30.6 (pre-release audit fixes):

  section read dictionary keys (ogc_compliant / dgiwg_compliant /
  geometry_valid / metadata_valid) that OutputValidator.validate_gpkg_structure()
  never produces, so the section always displayed failure even for a fully
  valid, DGIWG-compliant GeoPackage. A normaliser now maps the real
  structure-check keys (compliant, gdal_readable, dgiwg_spatial_indexes,

  used the builtin `any` instead of typing.Any.
- FIX (schemas/iso19139-gmd.xsd): the bundled ISO 19139 subset schema ordered
  metadataConstraints BEFORE dataQualityInfo in MD_Metadata, the reverse of
  real ISO 19139 and of what generate_package_metadata() emits. As a result
  EVERY package-metadata schema validation failed (silently, as a warning in
  the shipped tool) and all schema-validation unit tests failed. The element
  order is corrected and the previously-undefined LI_Lineage type is added so
  metadata carrying a lineage statement also validates.
- FIX (core/config.py): GDAL_LAYER_OPTIONS now pins GEOMETRY_NAME=geom, making
  explicit the geometry-column name that the DGIWG finalization step already
  assumes (rtree_<table>_geom).
- FIX (core/validators.py, concurrency bug): validate_output_path() probed
  directory write access with a FIXED filename (".gpkg_creator_test"). When
  several conversions targeted the SAME output directory concurrently, the
  threads raced on that one probe file and one would spuriously fail with
  "No write permission" / WinError 2. It now uses a unique per-call probe name
  (tempfile.mkstemp), so concurrent conversions to one directory are safe.
- ADD (core/validators.py): OutputValidator.verify_crs_in_srs_table(path, epsg)
  - checks whether an EPSG code is present in gpkg_spatial_ref_sys. It was
  referenced by the test suite but had never been implemented.
- FIX (tests/test_concurrency.py, CRASH): test_concurrent_writes_different_files
  spawned 3 threads that all called converter.convert() on the SAME source
  shapefile concurrently. On GDAL 3.13 this reproducibly crashed the entire
  pytest process with "Windows fatal exception: access violation" - a native
  crash, not a catchable Python exception - which also aborted every test after
  it in the run. GDAL/OGR does not support opening one file from multiple
  threads at once. Fixed by giving each thread its own private copy of the
  source file (extracted into a shared _copy_shapefile_for_thread() helper) in
  all three tests that spawn threads: test_concurrent_writes_different_files,
  test_concurrent_writes_same_file_serialized, and test_many_concurrent_threads.
  This mirrors real deployment usage (N concurrent conversions have N distinct
  source files) and is not a limitation of the shipped GUI/CLI, which never
  runs more than one conversion thread at a time.
- TESTS: modernised the pytest suite to match current (v0.27.0+) behaviour and

GeoPackage Creator v0.30.0
Release date: 2026-06-18

NEW in v0.30.0 (OGC + DGIWG compliance fixes):
- Fix 1 (OGC): GPKG_APPLICATION_ID_DGIWG changed from 0x47503132 (GP12) to
  0x47503134 (GP14), making it consistent with user_version=10400 (GeoPackage
  1.4). A file claiming GP12 via application_id but 1.4 via user_version fails
  OGC validation because both fields must agree on the spec version.
- Fix 2 (DGIWG Req 13): WKT2 generation switched from WKT2_2019 to WKT2_2015
  format. WKT2_2019 represents EPSG:4326 with ENSEMBLE["World Geodetic System
  1984 ensemble",...]; the DGIWG Req 13 offline check expects the datum name
  "World Geodetic System 1984" and does not alias the ensemble name, causing a
  hard FAIL. WKT2_2015 uses DATUM["World Geodetic System 1984",...] which
  passes the check while remaining fully WKT2-compliant.
- DGIWG Validator (checks.py _r3): expanded _GP_VERS table to accept
  0x47503133 (GP13, GeoPackage 1.3) and 0x47503134 (GP14, GeoPackage 1.4) as
  conformant for DGIWG Req 3, since DGIWG STD-DP-19-005 requires 1.2 or later.
- Version bumped to 0.30.0 across all files.
