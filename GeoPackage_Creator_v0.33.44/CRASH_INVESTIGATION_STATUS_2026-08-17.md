# GeoPackage Creator — Sequential-Conversion Crash: Investigation Status

Prepared 2026-08-17, after diagnostic run v0.30.37 (probes P58/P59). Covers the full arc from the original bug report through the four-way-validated candidate mitigation, plus a fresh reading of the shipped codebase (`geopackage_creator_gui.py`, `core/gdal_handler.py`, `core/converter.py`, `core/metadata_handler.py`) done today to check what all the runtime probes had been assuming rather than verifying.

This is a status report, not a patch. No production code has been changed, and nothing here should be read as a proposal to change any — that stays a separate, later decision, consistent with how every diagnostic script in this series has been delivered.

## The crash

Running two GeoPackage conversions back to back — thread A starts, runs to completion, is `join()`-ed, and only then does a brand-new thread B start — reliably kills the process with a Windows native access violation (exit code 3221225477 / 0xC0000005). It reproduces through the real, unmodified `GeoPackageConverter.convert()`, every time, on the target machine.

## Why the three earlier fixes don't explain it

`metadata_handler.py`'s own module docstring documents three previous rounds of crash investigation, each of which found and fixed something real. It's worth being explicit about why none of them account for what this series has been chasing, because otherwise it looks like the same bug being fixed a fourth time rather than a genuinely different one.

v0.30.10 found true concurrent compilation: three worker threads each constructed a `MetadataHandler` in their own `__init__`, before `convert()`'s serialization lock was ever acquired, so all three could call `etree.XMLSchema()` at the same instant. That is a textbook data race, and serializing every lxml touch behind `_LXML_LOCK` correctly closed it. v0.30.13 chased a libxml2 ABI mismatch (the extension compiled against 2.14.6, a 2.15.3 DLL loaded at runtime) and added a fail-fast guard — a real, independent defect, but v0.30.20 later proved it wasn't the cause of the ongoing crash: pinning both sides to a matched 2.14.6 still crashed. v0.30.20-23 then found the actual mechanism behind *that* round of crashes: a compiled `XMLSchema` object does not survive a GDAL GeoPackage write and silently corrupts if reused afterward, even once, even by the same thread. The fix was to stop caching a compiled schema at all — `_compile_schema_fresh()` recompiles from scratch on every single `validate_schema()` call, and nothing above it stores the result anywhere that outlives that one call.

The crash this series (P1 onward, most recently P17–P59) has been diagnosing still happens with all three of those fixes in place and untouched. There is no concurrent compilation here — thread A has fully finished and been joined before thread B is even created. There is no ABI mismatch on the machine these probes ran on. And there is no reused compiled schema — every probe's control uses the real `_compile_schema_fresh()`, which recompiles every time, exactly as v0.30.23 designed it to. This is a fourth, distinct mechanism, related only in the broad sense that "a GDAL write disturbs live libxml2 state" is the throughline across all four.

## What this series established

Real bisection — monkey-patching the actual shipped `MetadataHandler.validate_schema` and `_compile_schema_fresh`, never a hand-rolled approximation — pinned the necessary condition down precisely by P51/P52/P53 (v0.30.34): one OS thread must perform a real GDAL write and a real lxml schema-file touch itself, in that order, within that same thread. Only then does a later, different, freshly created thread's first lxml touch crash. Split the two activities across two threads that each do only one — GDAL-only in one thread, lxml-only in another — in either order, and nothing crashes, ever, in any run so far.

Some of the boundary conditions were established earlier and still hold: thread B needs no GDAL of its own (P37); document content and size are irrelevant, even a trivial `<x/>` crashes through the real pipeline (P40); parser configuration is irrelevant — hardened, default, or plain all behave the same (P42/P43); the full `etree.XMLSchema()` compile isn't even required — parsing the schema file alone, with its real cross-file `<xsd:import>` resolution, is sufficient to trigger it (P44); and pure lxml activity, with GDAL never involved anywhere in the process, never crashes no matter how it's arranged (P46/P47) — so GDAL is a genuine, necessary ingredient, not an innocent bystander.

One thing remains an open question rather than a settled finding: v0.30.28's hand-rolled probe P26 also had thread A do a GDAL write followed by its own lxml touch, sequentially handed off to thread B, and never crashed — superficially the same shape as what P52/P53 later confirmed is dangerous. That gap was never closed; it was deprioritized once the real-pipeline bisection (P36 onward) started reproducing reliably through the actual code instead of an approximation. A plausible explanation, worth stating as a hypothesis and nothing more, is that the fault sits in something thread-identity-scoped rather than purely global — a thread-local allocator arena, a TLS-indexed cache inside libxml2 or the CRT, something tied to a specific OS thread ID being retired and a new one allocated — which would make it sensitive to exactly how many other threads existed before it, how much each thread's stack touched, or other incidental differences between a minimal hand-rolled repro and the real pipeline. That would fit the data collected so far, but it has not been tested directly and shouldn't be treated as confirmed.

## The candidate mitigation, and four independent clean results

The shape being tested: never let any single thread perform both a GDAL write and an lxml touch itself. GDAL work stays on its own worker thread, as today. Every lxml/schema-validation call in the whole process, from any thread, is routed instead to one single, persistent worker thread — created once and reused for the process's life, never recreated. Since no thread would ever do "GDAL then lxml itself," and no new thread would ever be the one making its first lxml touch right after such a thread, the confirmed necessary condition would never arise.

Four separate runs have come back clean. P52 (v0.30.34) showed it safe for one round. P55 (v0.30.35) repeated it five times sequentially with zero crashes. P57 (v0.30.36) ran four GDAL-only worker threads started back to back — real overlap in their attempt to run concurrently — all dispatching to the one persistent thread, with the log itself proving a single OS thread identity handled all four jobs. P59 (v0.30.37) combined both dimensions: three batches of four attempted-concurrent workers each, twelve conversions total, all funneled through the same one persistent thread for the entire run, again a single confirmed thread identity throughout, zero crashes. Each new script's logic was verified before being sent — AST-level structural checks against the actual generated probe code (not a paraphrase of it), plus standalone behavioral tests with mock stand-ins exercising the dispatch protocol under real concurrent load (one test ran 1,600 concurrent dispatches with zero cross-talk) — since this sandbox cannot run GDAL or lxml itself and every result had to come from logs generated on the target machine rather than from guessing an outcome.

One correction to how P57 and P59 were originally framed, caught only today by reading `core/gdal_handler.py` rather than assuming: `GeoPackageConverter.convert()` is already decorated with `@_serialize_conversions`, which acquires a process-wide `RLock` (`_GLOBAL_CONVERSION_LOCK`, added in v0.30.7 for an unrelated, already-fixed handle-lifetime bug) around the entire call. That lock is shared across every `GeoPackageConverter` instance in the process, so when P57/P59's four worker threads all called the real `convert()` "concurrently," their actual GDAL work was still serialized by this pre-existing lock — only one thread was ever really inside `convert()`'s body at a time; the other three were blocked waiting on the RLock. So "real GDAL writes overlap in time," as those two scripts' docstrings put it, overstates what happened at the GDAL layer specifically. What was genuinely concurrent was the thread creation and scheduling itself, and the contention of multiple threads simultaneously dispatching to and waiting on the one persistent lxml worker's queue — which is still a real, previously-untested dimension, and still came back clean. It just isn't literally "two GDAL writes happening at the same instant," because the shipped code already made that impossible before this investigation ever started.

## What real usage actually looks like

Reading `geopackage_creator_gui.py` directly answers a question every probe so far had to assume an answer to: does the shipped GUI ever produce genuinely concurrent, same-process conversions? It does not, and it structurally cannot. `start_conversion()` checks `self.is_converting` and refuses to start a second conversion thread while one is in flight; the flag is set before the single `threading.Thread(target=self.do_conversion, ...)` is created and cleared in a `finally` block after that conversion ends. There is exactly one call to `threading.Thread(` in the entire GUI file. The only other way to start a conversion — "Convert in Console" — launches a wholly separate OS process via `os.startfile` on a generated `.bat` file, not a thread in this process, so it shares no Python interpreter, no GIL, and no loaded libxml2 image with the GUI; it's irrelevant to an in-process native crash. And underneath both of those, `core/gdal_handler.py`'s own module docstring says plainly: "The shipped GUI and CLI never run more than one conversion at a time," which is exactly why `_GLOBAL_CONVERSION_LOCK` was written to cost nothing in the normal case.

Put together: the crash this series has been chasing can only ever arise, in the shipped product as it exists today, through the strictly sequential pattern — convert one file, let it finish, convert the next. That is precisely what the original bug report described, precisely what every control probe (P17 through P58) has modeled, and precisely the scenario P52 and P55 validated the mitigation against most directly. The concurrent-attempt probes (P57, P59) add confidence for a hypothetical future where that guard is loosened or a batch-conversion feature is added, but they were testing beyond what today's shipped GUI can produce, not filling a gap in today's coverage.

## Scope, if this were ever implemented

Grepping the rest of `core/` turned up no other file that imports or touches lxml — `metadata_handler.py` is the only one. Within it, every real interaction with libxml2 funnels through exactly two functions: `_compile_schema_fresh()` (compiles the schema) and `validate_schema()` (parses the document and calls `.validate()`, internally invoking `_compile_schema_fresh()` too via the `schema` property). `reset_schema_cache()` is the only other function under `_LXML_LOCK`, and it only resets a cached filesystem path and a boolean flag — it never touches a real lxml object. So a mitigation would need to intercept exactly one call path — `validate_schema()`, called from `converter.py` at the package-metadata step and once per layer — and would not need to touch `core/gdal_handler.py` or its existing serialization lock at all, since that lock already does what it was designed to do and isn't implicated in this crash.

## What hasn't been done

No production file has been edited. No fix has been proposed for review or merge. The four clean mitigation results are strong, convergent evidence that the pattern is *safe*, gathered the same disciplined way as every other finding in this series — real bisection against the actual shipped code, verified before being sent, never assumed. But "safe in an isolated harness, four ways" and "correctly and completely wired into the shipped GUI and CLI" are different claims, and only the first one has evidence behind it yet. Lifecycle questions that only come up at integration time haven't been touched: where the persistent thread would be created and by whom (module-level lazy singleton in `metadata_handler.py` is the natural fit, given the GUI itself never manages worker-thread lifecycles today beyond the one `is_converting`-guarded thread), what clean shutdown looks like when the GUI closes, and how a CLI invocation — which starts, runs one conversion, and exits — would even benefit from a thread meant to be "created once and reused for the process's life" versus just being unnecessary overhead there.

## Where this leaves things

The diagnostic phase has produced a precise, reproducible necessary condition and a mitigation pattern validated four independent ways, including under conditions more demanding than what the shipped product can currently produce. Continuing to run more rounds or larger batches at this point would mostly be re-confirming what four clean results have already shown; the more useful next step, if there is one, is a different kind of work; either scoping and drafting an actual patch (still with the same discipline — proven locally before it's trusted, per the existing project workflow), or continuing to harden the diagnostic case further, or closing out the P26 mystery out of intellectual completeness before touching shipped code at all. That choice is exactly the one worth deciding directly rather than assuming.
